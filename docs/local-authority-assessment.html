Making the theatre server the authority

An assessment before any change, as the brief requires — grounded in a failure that occurred in production today and was diagnosed line by line, rather than in what the architecture might do in theory.

20 August 2026UNTH Theatre ORMAssessment only — no architectural change made
Executive summary

The outbox you asked for already exists. The equal-master problem you asked to remove also exists, and it caused an outage today.

ORM already has a durable local outbox (sync_journal), replay protection, a deferred-row park, a conflict quarantine and a hybrid logical clock. Much of sections 5, 7, 8 and 9 of your brief is built and working. What is missing is not machinery — it is authority.

Thirteen of the synced tables, including surgeries, are classified last-writer-wins. Two databases therefore compete on a clock to decide the state of a theatre booking. That is the equal-master arrangement your section 1 forbids, and it is live today.

The concrete harm is not hypothetical. This morning a neurosurgical case booked on the cloud could not reach theatre, and the outbound queue had an entry that had failed 785 times since yesterday. One root cause, described in full below: two masters minting identity independently.

Verified from the repository and both live databases, not assumed. Two premises in the brief do not hold and are worth correcting, because they change what needs building.

B · Current flow

Every direction is driven from the theatre server

LOCAL → CLOUD   worker reads sync_journal, POSTs to the cloud, marks ack_at
CLOUD → LOCAL   the SAME worker pulls from a cursor and applies locally
CLIENT → LOCAL  ordinary HTTPS on the hospital LAN
CLIENT → CLOUD  ordinary HTTPS from outside — and it writes DIRECTLY

The theatre server sits behind carrier-grade NAT, so the cloud has no route in. Both directions are therefore initiated locally, which is already most of the way to the topology you want.

The fourth line is the problem. A remote user booking through the cloud writes an authoritative surgeries row directly into the cloud database. There is no request state, no local validation, and no local confirmation. The cloud is not a gateway; it is a second master.

C · Failure points

Why records go missing, with today's evidence

1 · Identity is minted independently on two masters caused today's outage

Nwafor Chinedu Solomon, folder number 914954, was registered twice on 19 August: on the theatre server at 17:03:48, and on the cloud at 17:09:40. Six minutes apart — inside the sync interval, so neither node could see the other's registration. Each minted its own UUID.

folderNumber and ptNumber both carry unique indexes. Two rows describing one human, each holding the identifiers the other needs. Neither can ever cross.

  1. 19 Aug 17:03 — patient registered locally. Push to cloud fails: folder number taken.
  2. 19 Aug 17:09 — same patient registered on the cloud. Pull to local fails: folder number taken.
  3. 19 Aug 23:25 — neurosurgical case booked on the cloud against the cloud's patient id.
  4. 20 Aug 12:55 — the case has failed surgeries_patientId_fkey on arrival for thirteen hours. 64 pack rows are stacked behind it. The outbound entry has been retried 785 times; the inbound one 855.
  5. Resolved by merging the two records onto the earlier id, in one transaction, on the cloud.

Nothing about the link was broken. It was pulling every sixty seconds with zero errors, faithfully carrying a row that could not land. A dashboard reporting "sync healthy" would have been correct and useless.

2 · Last-writer-wins on clinical tables equal-master

Of the synced tables: 13 LWW, 20 append-only, 13 quarantine, 11 cloud-authoritative. surgeries is LWW, so a cloud edit with a later clock overwrites a theatre edit. Section 13 of your brief forbids exactly this.

3 · The recovery tool never worked

rejournal.sh re-queues a stranded row with UPDATE … SET "updatedAt" = "updatedAt" — a no-op, so the capture trigger supplies the clock and version for free. But sync_capture() opens with "an update that changed nothing of substance is not worth shipping" and discards it. The instrument written to recover stranded rows has never recovered one, and it exits 0 either way.

4 · What is not wrong

  • Push is not head-of-line blocked. The failing entry sat unsent for 785 attempts while newer entries acknowledged normally — so a stuck row delays itself, not the queue.
  • Nothing is silently discarded any more. Until 18 August an unknown table was answered IGNORE, which the sender treated as settled and deleted. That is fixed: UNKNOWN_TABLE is now its own outcome and the entry is kept.
  • Clinical content is already quarantined rather than overwritten — prescriptions, assessments, patient identity.
D · Proposed architecture

Three changes, not a rewrite

The brief asks for local authority, an outbox, idempotency, retries and request-state for remote bookings. Four of those five exist. What follows is what is genuinely missing.

D1 · One authority per table

Add LOCAL_AUTHORITATIVE to the policy and move surgeries, theatre_allocations and the pack tables onto it. An incoming cloud change to such a table is never applied; it is recorded as a request and answered by the local server.

The mechanism already exists — CLOUD_AUTHORITATIVE is its mirror image and is in use for identity and access. This is the same code path pointed the other way.

D2 · Remote bookings become requests

A cloud booking writes booking_requests, not surgeries, with status PENDING_LOCAL_CONFIRMATION. The worker pulls it, the local server validates and commits, and the outcome replicates back. The remote user is told "submitted", never "confirmed", until theatre has said so.

D3 · Identity that cannot collide

The real fix for today's outage. Registration must reconcile against the peer by folderNumber before minting a UUID, and the sync must match patients on folder number rather than on id alone. Without this, D1 and D2 leave the same trap open.

Judgement

Two things in the brief I would argue against

Double-booking exclusion constraints (§14)

A database-level bar on two confirmed bookings sharing a theatre and interval is correct in principle. In this hospital, cases run over, lists are rearranged mid-morning, and a room is legitimately double-booked on paper while a decision is made. A hard exclusion constraint would refuse writes during exactly those moments — and staff who cannot record reality in the system record it on paper instead, which is how ORM stops being the source of truth at all.

Recommendation: detect and flag the overlap loudly; refuse only where clinical policy genuinely says never.

"Local always wins" applied to clinical content (§13)

Right for scheduling: who booked which room is an operational fact and theatre owns it. Wrong for a prescription or an anaesthetic assessment, where two differing versions both represent something a clinician actually wrote. Silently discarding the cloud's copy because it lost a race is a patient-safety decision made by a timestamp.

Recommendation: local authority for operational state; keep quarantine for clinical content, as now. Authority per table, not one rule for the whole database.
