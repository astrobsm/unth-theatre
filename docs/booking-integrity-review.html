Forensic review · Operative Resource Manager

Missing packs and “Unknown” identities in surgical booking

Four reported defects, traced through the full booking lifecycle against production data on both databases. Three were real. Two of those had already been fixed weeks earlier; one was systemic and is fixed now. The fourth does not exist as reported — but the search for it found a different real defect.

19 August 2026 UNTH Theatre ORM Theatre server + cloud, live data
Executive summary

There is no single root cause, because these are four separate faults that share one symptom: a record that reads as absent. Two of them — the missing consumable pack and the missing pharmacy pack — were genuine, were fixed on 22 July and 17 August respectively, and the production data shows each stopping dead on the day its fix went live. The reports describe the legacy population those fixes left behind, not ongoing loss.

The third — the booking user showing as “Unknown” — was systemic and affected 45% of every case ever booked. Its cause was architectural: the booker’s name was never stored on the booking. It was read out of the case’s consumable pack lines, so any case without a pack had no identifiable booker. That is fixed and backfilled.

The fourth — the patient’s name becoming “Unknown” — could not be reproduced and does not exist in either database. Patient identity is protected by a required column, a foreign key, and a server-side existence check, and the booking form submits the patient id from the DOM rather than from React state, which rules out the state race that would otherwise explain it. What does exist, and is very likely what was seen, is pack line items stored with the name “Unknown”.

Correction

The architecture is not the one described

Several of the failure modes in the brief cannot occur here, and saying so narrows the search considerably. Verified in the dependency manifest and source:

AssumedActualConsequence for this investigation
Supabase database & auth, RLS policiesPostgreSQL via Prisma; NextAuth with JWT sessions. Supabase appears only as an optional blob store for scanned documents (SupabaseDocumentStore, plain REST) — there is no Supabase client anywhere near the booking path.RLS, Supabase upsert semantics and PostgREST behaviour are all out of scope.
IndexedDB / Dexie local records with id remappingNeither is a dependency. No local id space, no mapping table, no UUID→integer transformation.Id collision and remapping cannot cause loss. Ids are UUIDs generated by the database and are stable across both nodes.
Offline queue replaying booking POSTspublic/sw.js line 215: if (request.method !== 'GET') return; — the service worker never intercepts a mutation.There is no offline booking queue. A booking attempted offline fails outright; it is never queued, mutated, retried or replayed. This eliminates the entire serialization-and-retry class of cause.
Naïve last-write-wins syncA custom journal with a hybrid logical clock and an explicit per-table policy — APPEND_ONLY, LWW, QUARANTINE, CLOUD_AUTHORITATIVE — plus a replay guard, a deferred-row park for ordering failures, and a human conflict queue.Clinical content is already quarantined rather than overwritten. The sync engine is not the naïve design the brief warns about.

The service worker does cache GET responses network-first, so a stale read is possible when the network is down — but it cannot destroy a stored record.

Closed

They were not a hole in the guard. They were the guard not running yet. The theatre server’s own git reflog and build stamp place all four inside a twelve-hour window in which the fix was in the working tree but not in the served bundle:

  1. 17 Aug 21:23 UTC — b25e8e2 committed: pharmacy pack required.
  2. 18 Aug 09:14 UTC — theatre server pulls 7805137, the first commit containing the guard. Source is now correct.
  3. 18 Aug 11:24 → 15:13 — the four bookings are taken. Next.js is still serving the previous build, which has no guard.
  4. 18 Aug 21:32 UTC — .next/BUILD_ID written. The guard finally enters the running application.
  5. 18 Aug 21:32 onward — not one further case is missing a pharmacy pack.
Root cause
The application code was correct; the deployment was a pull without a rebuild. A compiled Next.js application does not pick up a changed route by having the file on disk.
Why intermittent
It was never intermittent. It was total before 18 August and zero after — the appearance of intermittency comes from mixing the two populations together in one list.

This is the same trap deploy.sh was written for. It was hardened further today — see Fixes applied.

Report C

The booking user

The booker’s name was never stored on the booking

Systemic · fixed today

The surgeries table had no bookedById column. The case-readiness card obtained the name by looking at the case’s consumable request rows and reading requestedBy off whichever one carried it.

So the booker existed only if the case had a consumable pack — and the card names the booker precisely so that somebody can chase a pack that is missing. The single situation in which the name is needed was the situation in which it had been derived out of existence. The screenshot that opened this investigation shows both halves at once: “Consumable: Not prescribed” beside “Booked by: Unknown”, above a WhatsApp button with no number behind it.

266 / 592cases that could never show a booker — 45% of everything ever booked
563 / 592attributed by the backfill

It also made the answer depend on which database was asked. Pack rows replicate separately from the surgery, so a case booked in theatre read correctly there and as booked-by-nobody on the cloud until they caught up — 7 such cases in the last fortnight on the cloud against 2 locally. An identity derived from a child row is not an identity; it is a coincidence of replication order.

Fix
surgeries.bookedById and bookedByName, written at booking on both the elective and emergency paths. Both are stored: the id is the only route to a phone number, and the name is what still reads correctly on a node that has never seen that account. Soft reference, no foreign key — users is cloud-authoritative and a booking must never be refused on a node that has not yet received the booker.
Backfill
audit_logs has recorded CREATE_SURGERY with the user id far longer than the pack rows carried a requester. It identified 491 cases, including 237 that have no consumable rows and no other recoverable source. Pack rows filled a further 72.
Left alone
29 cases from June and July, 26 of them emergencies, predate both sources. They read “Not recorded” rather than “Unknown”, because nobody wrote it down and inventing a booker for a clinical record is not a rounding error.
Verified
All 13 of today’s cases name their booker. Both databases hash identically across all 592 rows.

And the write path forecloses the race the brief describes:

  • The payload does not read React state. The patient is a controlled <select name="patientId"> and the submit handler builds its payload with formData.get('patientId') — it reads the DOM at the instant of submit. A stale selectedPatient could not reach the server even if one existed.
  • The column is NOT NULL and required by the request schema; a booking without a patient cannot be validated.
  • The server verifies existence before creating anything, returning 404 Patient not found.
  • A foreign key enforces it in both databases, with zero orphans across 592 cases.

If a patient name is seen as “Unknown” again, note the folder number and the time: audit_logs stores the exact submitted payload for every registration, so the question can be answered from the record rather than from memory.

What the search did find: pack lines stored as “Unknown”

Real · fixed today

Searching the audit payloads for an Unknown name returned two bookings — and the match was not a patient. It was a pack line:

{"templateId":"691314ce-9c7b-416d-92e5-55691e8b8c47",
 "name":"Unknown","category":"OTHER","size":null,
 "unit":"piece","quantity":2}

The booking form resolves each item’s label from whichever slice of the template catalogue that screen had loaded. When the slice does not contain the template — a subspecialty filter changed after the item was picked, a search narrowed the list — it falls back to 'Unknown', and takes category down to OTHER and size and unit to defaults along with it.

20 lines across 2 cases, every one carrying a templateId that resolves perfectly well. The pack provider was asked to find “Unknown ×2” when the case had requested a urine bag. The lost size mattered as much as the name: cannula gauges were being nulled out.

Fix
The label was never the fact — the templateId is, and the server holds the catalogue. The server now resolves name, category, size and unit from the template and keeps what the client sent only for free-text lines, which genuinely have no template.
Not overridden
Dosage and route on the drug side. The form offers the template’s defaults and lets the prescriber change them, so what arrives is a decision about this patient — replacing it with a catalogue default would be the same error pointed at something that matters more.
Repair
All 20 rows restored from the templates they already pointed at, verified in a rolled-back transaction first. Lines already packed were repaired too: somebody had to work out what “Unknown” meant in order to pack it, and leaving the record wrong so it still matches what they were shown preserves the confusion rather than the history.

Recommendations

Making the next one visible before it is reported

Every fault in this report was found by querying production, weeks after it began. The single highest-value change is not another constraint — it is a daily integrity check that would have surfaced all four.

  • A booking integrity view, checked daily. Cases booked in the last 24 hours with no consumable rows, no drug rows, or no bookedById. Each of the three faults in this report would have appeared on day one instead of week six.
  • Alert on the build/source gap. The four pharmacy cases existed because the code on disk was twelve hours ahead of the running build. Compare git rev-parse HEAD against the commit the build was made from and warn when they diverge — this is a deploy-discipline fault that no amount of application code prevents.
  • Reconcile the two databases on a schedule. Row counts and column hashes for the booking tables, the way this review compared them by hand. Divergence with nothing parked in sync_deferred is invisible today and means rows that will never converge without intervention.
  • Do not add NOT NULL to bookedById. 29 historical cases legitimately have no answer, and a constraint would either block the migration or force a fabricated value into a clinical record. The check belongs in monitoring, where “not recorded” can stay distinguishable from “wrong”.
  • Keep the distinction the brief asks for. “Not recorded” now means the record is absent; it is deliberately different from “Unknown”, which implied the person could not be identified. Missing packs are already flagged rather than hidden — that behaviour was correct and is unchanged.
